# 测试与发布门禁

> 类型：实施指南。Schema/API 冻结、平台支持和 v1 发布验收以本文为唯一权威来源。

## 测试原则

- 领域不变量和公开契约先于实现细节；
- 合成测试用于可重复和极端边界，真实只读样本用于验证规则覆盖，二者不得互相冒充；
- 平台支持必须在目标系统实际运行；交叉编译只能满足“可构建”；
- 性能报告必须记录样本、硬件、存储、版本、冷/热状态和分位数；
- 生产媒体根只允许只读验证，并用前后清单/guard 证明零变化；
- 高风险真实全库扫描、批量派生和维护任务不作为普通 CI。

| 层 | 每次提交 | 定期/发布前 |

| 数据 | Schema 升级、事务、备份恢复、revision、Saga、游标 | 强杀、磁盘满、损坏、GC/VACUUM |

| UI | mock API、键盘、焦点、能力显隐、断线恢复 | 主流浏览器、移动 viewport、壳 WebView |
| 平台 | Windows 核心 smoke | Windows 完整、Linux ext4、macOS、Docker、SMB 按支持目标 |

## 跨平台一致性与主分支 CI 状态

- Web 格式检查的权威命令只有一条：`web` 目录下的 `npm run format:check`（`prettier --check .`）。根级 `Check.ps1` 与 GitHub Actions 的 Windows、Ubuntu 两个 Job 都必须调用它，不允许某个平台改用别的参数、跳过该步骤或先执行 `prettier --write`。
- 同一提交在 Windows 与 Ubuntu 上必须得到同一结论。结论不一致时，先假定是环境把仓库内容改写成了不同字节（最典型的是检出换行），再考虑代码本身；tracked 文件换行的唯一事实源是 `.gitattributes`，不是任何用户或 runner 的 `core.autocrlf`/`core.eol`。
- `Check.ps1` 在执行任何语言门禁前先断言 tracked 文件的 index 与工作树换行均为 LF，使本地门禁与 CI 在换行问题上等价，失败时直接列出违规文件。
- VitePWA/Workbox 生成的 precache URL 必须非空、按不依赖 locale 的稳定二元序排列且无重复；固定为同一 Node/npm 与 lockfile 时，Windows 和 Ubuntu 构建不得改写 tracked Web 生产资产。生成器升级或资产集合变化后仍由 `internal/webapp` 的最终产物测试和根级生成摘要共同 fail-closed。
- 主分支 CI 失败不得无限期标记为“既有问题”。同一失败签名在 `main` 上连续出现第二次时，必须立即登记为待修复缺陷并在下一轮作为正式任务处理；在其关闭之前，不得声明任何依赖该 Job 的门禁通过，也不得把“CI 一直是红的”当作可接受的稳态。
- 跨平台格式失败只能通过修正仓库事实源解决。禁止把 `endOfLine` 改为 `auto`、删除或跳过某个平台的 Job、对失败命令加 `continue-on-error`、忽略退出码，或把普通源码批量写入 `.prettierignore`。

## 正式验证规模分级

阶段 3、阶段 4 及未来阶段共用同一套规模分级，不按阶段各自定义规模。规模单位是**单个聚合 Catalog
的 WorkProjection 总数**，不是每个来源的数量。

| 等级 | WorkProjection 数量 | 用途 | 是否标准 Gate |
| --- | ---: | --- | --- |
| `smoke` | 1,000 | 工具启动、契约、进程和最小 Correctness | 是 |
| `integration` | 10,000 | 主要过滤、搜索、Cursor、媒体和报告结构 | 是 |
| `preflight` | 100,000 | 正式规模测试前的成本、空间和超时预检 | 是 |
| `reference` | 500,000 | 推荐的正式 Correctness、Reference Performance 和 Degradation 目标 | 是 |
| `nonrecommended` | ≥1,000,000 | 非推荐、显式启用的诊断场景 | 否 |

500,000 是当前推荐的正式验证规模，默认按 10 个目标来源（见下方"目标来源覆盖"）均摊为每个来源
50,000，共 500,000；若事实规则要求个别来源调整分布，可在保持总数 500,000 且每个来源均有实质性
样本的前提下调整，调整原因必须写入 run manifest。

`≥1,000,000` 规模只能作为显式启用的非推荐诊断场景运行，标准命令、CI、默认脚本和 README 快速流程
不得自动生成或运行；框架若保留手工诊断能力，必须要求显式 `--allow-nonrecommended-scale`、显式
`--scale`、显式独立输出目录、显式确认磁盘空间、显式超时，并在控制台和结果中标注
`NONRECOMMENDED_SCALE`——不属于正式支持规模，不构成标准 Gate。此规模分级由 2026-07-21～
2026-07-22 的首轮 1M/10M 实测结果（见 [验证记录 EV-35](../证据/验证记录.md) 与
[阶段3-4大规模测试归档](../证据/阶段3-4大规模测试归档.md)）驱动确立：10M 构建本身即可能超过 120
分钟且峰值占用约 91.47 GiB，1M 完整性能矩阵推算耗时约 97 分钟且高并发场景明确未达标，两者均不
适合作为可重复运行的标准发布 Gate；不代表产品架构确定无法支持千万级规模。

## Walking Skeleton 开工约束

Walking Skeleton 可以在完整 Schema/API 冻结前开工，但切片内已使用的基础契约必须是正式模型：两库迁移框架、Canonical/Source ID、SourceRuleBinding、首次完整 Blob hash、`query_publication_id`、OpenAPI DTO/错误信封和 capability 检查。验收应主动拒绝内存替代库、路径主键、临时 DTO、匿名管理员和客户端直连数据库。尚未实现 FTS、Overlay 写入、快照分页和多强杀点不构成开工阻塞，它们由 Architecture Proof Slice 冻结前补齐。

## 门禁分级

### Correctness Gate

所有正式支持环境必须满足，不能用“设备较慢”降级：

- Source 媒体根零写入，AppDirs 与 Source 不重叠；
- 同一 AppDirs 同时只有一个进程取得写所有权：第二个实例在打开或迁移数据库、建立监听、改写 descriptor 前即失败，锁在进程退出或强杀后释放，遗留锁文件不永久阻止启动，不同 AppDirs 可并行；
- 长任务经有界调度器执行：并发上限、资源类别隔离、取消与 graceful shutdown 生效，队列满不阻塞且持久 Job 保持 queued；同一逻辑 Job 同时最多一个 active Attempt，过期租约由启动及周期 reconciliation 按退避恢复，不丢失 publication 一致性；
- 对外查询只能通过合法 `query_publication_id` 选择快照，不接受裸 revision 组合，也不混合 Catalog、Overlay projection、SortKey 和 FTS 代次；
- 取消、崩溃、磁盘满和跨库 reconciliation 后旧数据仍一致且可解释；
- 取消/完成/失败的 Job 与 active Attempt 必须同事务收敛；retry-backoff 取消不得再次入队，Scan 显式取消必须级联活动 Hash，纯进程关闭只能形成 retryable `PROCESS_INTERRUPTED`；取消先于 `BeginPublishing` 时不得发布，进入 publishing 后拒绝迟到取消，已提交 Catalog publication 必须按权威事实恢复 completed；
- Catalog 删除重建后 Canonical、Binding、Overlay 和固定 Blob 稳定引用不丢失；
- SourceWork 拆分/合并按稳定来源证据检测，无法安全自动处理时经 Binding issue 阻塞该 Source publication，人工决策以 control.db pre-seed Binding 表达；撤回仅适用于尚未被扫描消费的决策，消费后返回 `CONFLICT` 且决策、issue、Binding 不部分修改，已生效结构变化需新的人工决策或未来补偿流程。Catalog 全量重建后决策恢复、Canonical ID 不漂移、被否定候选不复现，其他 Source 不受影响；
- capability、资源范围、Session/Token/WS 吊销不可绕过；
- 路径解析不能越界，句柄复核和离线状态不能退化为不受控读取；
- 所有失败使用稳定 code，不泄露绝对路径、secret、内部 row ID 或私密 metadata。

### Reference Performance Gate

性能阈值只对明确登记的官方参考硬件成立。每次结果必须同时记录 CPU、内存、存储型号/介质、操作系统、SQLite/搜索库版本、冷/热缓存、并发数、样本规模、运行次数和分位数；缺少任一项的旧数字只能作为方向性证据，不能宣称通过正式门禁。

- 500,000 WorkProjection（推荐正式验证规模，见「正式验证规模分级」）、每个投影两条关系、完整 SourceMedia/ContentBlob/FileLocation/FTS，1%/10%/50% 变化的 publication P95 <250 ms；≥1,000,000 属于非推荐诊断场景，其结果只作方向性证据，不代表本 Gate 的通过或不通过；
- 搜索 P95 必须按查询类别、limit、候选量和是否包含原文复核分别设阈值，不能以单个选择性查询代表全部搜索；
- staging 构建、Overlay 重投影、GC、VACUUM、峰值临时空间和完整哈希吞吐必须各有预算；当前证据仅提供基线，正式阈值在参考硬件复跑后冻结；
- **migration 耗时预算属于本 Gate，不属于可移植单元测试**。历史上 `internal/storage` 的合成规模迁移测试用固定 5 秒墙钟作为通过条件，在共享 CI runner 上连续假阳性（同一段迁移本机 NVMe 约 0.04 秒，GitHub Windows runner 实测 22.95 秒与 3.51 秒），改用同机整表改写校准也不成立——该迁移的主要成本是窗口函数排序器的临时文件 I/O，主库页写入无法代表它。单元测试现在只保留与机器无关的 `EXPLAIN QUERY PLAN` 结构断言（每张放大表单侧扫描一次、另一侧索引查找、禁止相关子查询），耗时改为记录值；数值预算在本 Gate 的登记硬件上测定。

EV-39（2026-07-23）核对了这些结论的可复验性：`tools/testlab/stages/stage4` 的查询与媒体 Correctness 断言（约 1,100 行）**没有任何 `go test` 入口**，只能人工 CLI 触发，`go test ./...` 与 CI 都不执行；该目录现有的 `perf_test.go`/`cursor_test.go` 断言的是测试框架自身而非产品。因此 EV-36 的「39 项 Correctness + 6 项 Cursor 通过」是一次性人工快照，不构成持续门禁——在为其建立 smoke 规模自动化入口之前，任何后续提交都不得据此声称阶段 4 Correctness 仍然成立。`internal/query/reference_performance_test.go` 同样默认 `t.Skip`（需 `GALLERY_REFERENCE_PERF=1`），且只输出分位数、没有阈值断言，属测量脚本而非门禁；其默认规模为 100,000，与本文件推荐的 500,000 不一致。

EV-45（2026-07-26）关闭上述 `TEST-2` 持续门禁缺口：`TestStage4CorrectnessSmoke` 以 1,000 Work、临时 AppDirs、合成 Source、生产 bootstrap 与真实 loopback HTTP/生成客户端，持续执行当时的 39 项查询、6 项 Cursor 和 20 项媒体/DerivedAsset finding；完整 finding 名集合、脱敏报告、首次 index scan 后至按需确认/Derived 完成期间的合成 Source 零写入与零 media limitation 均是普通 `go test` 的失败条件，根级 `Check.ps1`、Windows/Ubuntu CI 和 Linux race 因此会执行该入口。当时查询报告显式登记的 `creator.id` limitation 已由 EV-90 替换为第 40 项 query finding；EV-55 则让格式合法但不存在的 `queryPublicationId` 统一返回 OpenAPI 规定的 `409 CURSOR_EXPIRED`，不再保留原“裸伪造 publication 错误码差异”。smoke 不运行 perf，也不替代 500,000 十来源 Correctness、Reference/Degradation Performance、真实 HDD/SMB/NAS 或 API Freeze。

2026-07-23 完成 500,000 规模首次正式验证（见 [验证记录 EV-36](../证据/验证记录.md)）：Correctness（39 项）与 Cursor（6 项）断言全部通过，Perf 矩阵 63 个组合在 25 分钟场景预算内全部完成（未触发 `AbortedByTimeLimit`），但 `wide-cjk`/`structured-and`/`structured-or`/`overlay-favorite` 并发 16 下仍为 2-9.5 秒量级，根因（排序 CTE 无法提前截断、结构化过滤缺索引、`SetMaxOpenConns(4)` 连接池上限）与 EV-35 一致且均未修复；本轮测得的 Stage/Overlay 一次性批量构建耗时与本节定义的"1%/10%/50% 变化 publication P95"不是同一度量，未产出可直接对照该阈值的结果。**Reference Performance Gate 仍未通过。**

### Degradation Gate

HDD、NAS 或低性能设备允许超过参考机性能阈值，但必须保证：

- 旧 `query_publication_id` 在构建、GC 和维护期间仍可浏览；
- 长任务有单调进度、可取消且不长时间持有 publication 锁；
- 空间预检失败时在 publication 前终止，保留旧数据；构建中磁盘满也不得破坏活动 revision；
- 维护窗口、积压和预计空间对用户可见；
- 性能退化不能改变快照、授权、路径安全、错误 code 或崩溃恢复语义。

- Reference Performance Gate 按上节参考环境执行 publication、构建、Overlay 重投影、GC/VACUUM、空间和哈希指标；不得把 `<250 ms` 解释为慢设备的正确性要求；

保留阶段与根因；只有确认旧库已恢复到原 `control.db` 路径时，失败才可消费 pending 并继续启动。没有旧库可回滚
或回滚本身失败时必须保留 pending 与轮换副本，记录失败并以 `RESTORE_FAILED` 阻止 bootstrap，禁止让后续
`storage.Open` 在缺失路径创建空库。确定性文件操作 seam 的 Windows 测试和 WSL2 race 只关闭代码正确性边界；
真实 Windows 候选落位 sharing violation、磁盘满、ACL、断电/中断仍须以便携制品单独取证，阶段 7 Gate 不变。

EV-110 将真实 Windows 候选落位 sharing violation 纳入便携制品门禁：探针必须在启动前只监视系统临时 AppDirs
的精确 `data/control.db.incoming`，并在候选出现时以共享读写但拒绝删除/重命名的 handle 持有；不得修改产品
二进制或注入测试 build tag。当前库轮换必须成功，候选落位必须由 OS 拒绝，旧库随后回到原路径；服务应继续
发布 descriptor，备份后用户事实保留，pending 消费，`restore-last` 精确记录“落位恢复候选”，程序树封印不变且
全部进程优雅停止。该门禁证明真实落位失败后的安全回滚，不替代落位与回滚双失败、磁盘满、ACL/断电或 RC Gate。

EV-119 将落位与回滚双失败推进到包内真实 Windows 文件系统门禁：测试须用不共享删除的真实 handle 同时持有
`control.db.incoming` 与已轮换旧库，使生产文件操作中的两次 `os.Rename` 都实际返回
`ERROR_SHARING_VIOLATION`。结果必须是连续性错误，启动失败处理必须返回 `RESTORE_FAILED`、保留 pending，
`restore-last` 同时记录“落位恢复候选”和“回滚当前 control.db”，且轮换副本与候选字节均保留；解除 handle 后
旧库必须仍可恢复原位。该门禁不注入虚假 Rename 错误，但没有启动便携 `galleryd` 进程，不替代磁盘满、ACL/低
权限、杀进程/断电中断、人工恢复、正式签名或 Windows RC Gate。

EV-121 进一步要求恢复失败处理不能只识别“已经轮换后的连续性错误”：任何普通 apply 失败在消费 pending 并继续
启动前，都必须确认当前 `control.db` 仍是普通文件；当前库缺失、不可检查或不是普通文件时，必须把原始 apply 错误
与当前库不可用原因一并写入 `restore-last`，保留 pending，并以 `RESTORE_FAILED` 在 descriptor 前退出。便携门禁
预先保全当前库、写入并用真实 Windows handle 持有 stale incoming，使候选生成前确定失败；失败进程不得发布
descriptor，原路径不得出现新空库。解除 handle、恢复已保全当前库后，同一 pending 必须自动成功、备份后哨兵
消失且所有正常服务优雅停止。该门禁不替代便携同进程双 Rename 失败、容量/权限/中断、正式签名或 RC Gate。

EV-122 要求候选成功落位与恢复后安全收尾之间也具备跨进程恢复语义：落位后必须先原子持久化
`placed_pending_finalize`，不得在 `FinalizeRestore` 前消费 pending 或提前记录成功；下一次启动见到该阶段时只验证
当前 `control.db` 可用并重复幂等安全收尾，不得重新应用备份。安全收尾提交后，只有 `restore-last` 原子写入和 pending
消费都成功才允许对外启动；任一状态写入失败须保留 pending 并返回 `RESTORE_FAILED`。便携探针可在服务停止后构造
这一精确持久阶段，要求未打测试 tag 的真实 `galleryd` 保留阶段建立前的当前事实、吊销旧 Session、消费 pending 并
记录成功；该确定性重启门禁不替代指令级强杀/断电、磁盘满/ACL、便携双 Rename、正式签名或 Windows RC Gate。

EV-123 把 EV-122 的结果写入与 pending 消费失败推进到真实便携进程门禁。探针必须只在系统临时 AppDirs 中用
非空目录占用 `restore-last.json`，并另用不共享删除的真实 Win32 handle 持有 `restore-pending.json`；后者须先证明
本地删除确实返回 `ERROR_SHARING_VIOLATION`。两次真实未打测试 tag 的 `galleryd` 都应在 descriptor 前返回
`RESTORE_FAILED`，保留 pending、当前库与安全收尾后的用户事实；移除目录或释放 handle 后，同一恢复请求必须完成
结果记录、pending 消费并正常启动。目录冲突只证明文件类型异常，不替代 ACL/磁盘满；两条链也不替代实际强杀/
断电、便携同进程双 Rename、正式签名或 Windows RC Gate。

EV-124 要求双 Rename 也在同一个未打测试 tag 的真实便携进程中发生：探针先以共享删除的跟踪句柄允许
`control.db` 首次轮换，观察原路径消失后通过 Win32 `ReOpenFile` 对同一已轮换文件建立不共享删除的句柄；另一句柄
同时持有真实 galleryd 生成的 incoming。候选落位与旧库回滚的实际 `os.Rename` 都必须返回
`ERROR_SHARING_VIOLATION`，进程在 descriptor 前以 `RESTORE_FAILED` 退出，pending、incoming 和唯一新增轮换副本
保留，且轮换副本 SHA-256 等于失败前当前库。释放两句柄后，同一 pending 必须成功应用；原轮换副本继续字节不变。
该门禁不替代磁盘满、ACL/低权限、强杀/断电、正式签名或 Windows RC Gate。

EV-125 要求在真实便携进程中命中“候选已落位、`placed_pending_finalize` 已原子持久化、descriptor 尚未发布”的
精确窗口。Windows 观察器必须在进程启动前对状态目录建立异步目录通知，仅匹配目标 marker 的 Rename，且不得打开
`restore-pending.json` 或以轮询句柄干扰被测原子替换；命中后取消启动 context，进程 helper 只有在对仍存活的
`galleryd` 成功执行 OS Kill 时才可返回 `ForcedKill=true`。强杀后必须验证 marker 身份/阶段、descriptor 缺失、
唯一新增轮换副本与强杀前当前库 SHA-256 相同；同 AppDirs 重启后旧 Session 失效、备份后哨兵消失、恢复成功记录与
pending 消费收敛。该门禁不替代电源中断、其它指令窗口、磁盘满、ACL/低权限、正式签名或 Windows RC Gate。

EV-130 要求当前功能实测包必须来自包含最新双前端的精确干净提交，并重新走正式 Windows 便携构建与独立
`Test-WindowsPortable.ps1`，不得复用旧版本制品冒充当前界面。当前 `0.3.0-ev130` 已验证版本/提交、包内外摘要、
三份 CycloneDX SBOM、同源内嵌 Web 与同 AppDirs 强杀重启，清单为 `dirty=false`、`unsigned`。该门禁只建立可交付
pre-RC 测试入口；没有 Authenticode/时间戳、安装/更新、真实用户数据或完整平台门禁时，仍不得称为 RC。

EV-131 要求 Windows ACL 权限失败门禁使用真实 DACL，不得把伪造错误、只读属性或文件类型冲突冒充权限证据。门禁须
同时拒绝当前用户对 `control.db` 的 `DELETE` 与父目录的 `FILE_DELETE_CHILD`，并证明数据库仍可读写、实际 Rename
收到 OS `ERROR_ACCESS_DENIED`、当前事实和失败记录保留；测试结束必须恢复两处原始 DACL，后续完整恢复链继续通过。
当前证据只适用于本机当前用户和本地 NTFS；低完整性令牌、其它账户/服务、继承 ACL、ReFS/SMB 与磁盘满须分别取证。

EV-133 将 Windows v1 的历史升级支持改为仓库清单驱动的连续矩阵。清单必须登记当前 control schema、最低支持
schema，以及最低值到当前值前一版的每个历史 schema/精确祖先 commit；重复、跳号、非祖先、提交身份漂移或历史
源码 dirty 均 fail-closed。每条基线都须由真实旧程序创建 Library、control 备份与只显示一次密文的 API Token，
当前程序升级后核对备份 `WillMigrate`、事实、Token 元数据和实际 Bearer 鉴权；旧程序再打开新库必须在 descriptor
前拒绝且数据库字节封印不变，当前程序随后复启。便携发行清单必须以 schemaVersion 2 记录 current/minimum/verified，
新包不得使用 legacy manifest；旧包仅可在升级链的“上一版本”位置显式允许 schemaVersion 1。当前连续范围为
20/21/22/23→24；schema 20 以前的开发快照、磁盘满、低完整性/多账户/继承 ACL、其它文件系统、正式签名及 Windows
RC Gate 仍须独立取证。

EV-111 将 Scanner 已有多 `verificationTargets` 语义暴露为兼容公共批量端点，并把 `sourcelab` 的有界确认改为
每 Source 一个批量 Job。门禁必须同时覆盖生成 OpenAPI/TypeScript 客户端、请求上限/唯一性、同 Source/current
publication 原子验证、目标集合规范化幂等、单媒体兼容路径和真实 Pawchive 12 目标零写入链。用户端仍只呈现既有
单媒体操作，不得据此声称新增批量 UI；200 项是 PRE_FREEZE 请求上限，不是 Hash 并发或性能承诺。

EV-112 要求真实取消报告把“观察到 Hash running”与“取消后父子终态”分开记录，不得只以
父 Scan 超时或最终 cancelled 推测中间真的发生过活动 Hash。当前 Windows 本地 SSD/Pawchive 基线为
13 findings/0 failures，确认阶段 66,889 ms，取消后 4 ms 观察父 Scan/Hash 都为 cancelled，全树
11,595 文件/2,353 目录/124,660,469,885 bytes 增删改为 0。该结果是单平台、单本地 SSD 切片。
