# ADR-010 已确认媒体的正文读取语义

- 状态：接受
- 日期：2026-07-26
- 规范：[文件系统与媒体处理](../规范/08-文件系统与媒体处理.md)、[API、实时协议与安全](../规范/07-API-实时协议与安全.md)

## 问题

[验证记录 EV-39](../证据/验证记录.md) 记录的 P1 缺陷 `MED-1`：每一次媒体正文 `GET`/`HEAD`（含匿名分享正文）都先把整个源文件复制进 AppDirs 临时目录并计算完整 SHA-256，再从副本返回 Range 片段。

由此产生四个后果：

- 读取一个 4 KiB 区间要付出「整文件读 + 整文件写 + 整文件哈希」的代价，视频拖动会产生数量级的额外 I/O；
- `HEAD` 只需要 size 与 ETag，却付出同样的全量代价；
- 没有并发闸、没有磁盘空间预检，任意客户端反复请求大文件即可耗尽 AppDirs 所在卷；
- [规范 08](../规范/08-文件系统与媒体处理.md) 早已写明「原文件可直接流式读取时不复制到缓存」，实现与规范长期不一致。

不能简单删掉哈希：该实现同时承担着「返回的字节与已发布 ContentBlob 一致」这一产品不变量。必须先裁决用什么证据支撑这个不变量。

## 决策

已确认媒体（`content_verification_state = content_verified`）的正文读取改为**直接从 Source 流式返回请求区间**，不产生任何副本，并按下列分层证据维持不变量：

1. **打开阶段**把当前文件与 publication 冻结的 size 与 mtime 逐项比对。任一不符在发送任何字节之前返回稳定的 `CONTENT_CHANGED`（HTTP 409）。为此 catalog v13 把发布时刻的 mtime 固化进 `media_projections.mtime_ns`——证据必须来自快照本身，读取时回查 `source_media` 会跨越快照边界，也无法保证与该 revision 的投影属于同一代次。
2. **打开阶段与每次区间读取结束前**复核解析后路径与句柄仍指向同一文件（`os.SameFile`），且 size 与 mtime 在读取期间未变。
3. **整文件读取（非 Range）**顺带复算 `sha256-v1` 并与已发布 digest 比对。这不产生额外读 I/O——这些字节本来就要读——因此能免费发现「同大小、恢复时间戳、只改中间字节」这类身份证据无法覆盖的替换。
4. **读取过程中才发现的不一致**无法改写成错误信封，服务端中断响应（`http.ErrAbortHandler`），让客户端在 `Content-Length` 不足与连接异常两个层面都无法把截断结果误判为完整正文。

因此不变量的表述从「每次读取都重新证明 digest」收敛为：**读到的字节要么与已发布 ContentBlob 一致，要么调用方得到稳定错误或被中断的响应；服务端在任何情况下都不会静默返回与已发布 digest 不一致的正文。**

配套边界：

- `HEAD` 只做安全路径解析、身份证据比对与 stat，**读取零字节**；它回答的是 publication 记录的 size 与 ETag，不对字节作出断言。
- 单次请求的常驻资源与文件大小无关，因此**不再需要文件大小上限与磁盘空间预检**——这两项在 `MED-1` 中被列为缺失，是全量复制方案的产物，流式方案下它们不再保护任何东西，加上只会成为无意义的配置面。
- 保留**并发正文读取闸**：限制同时打开的 Source 句柄数与并发磁盘寻道。名额耗尽时有界等待后返回可重试的 `MEDIA_READ_BUSY`（HTTP 503），不让请求无限排队。默认并发 16、等待 5 秒，均为 PRE_FREEZE。
- 身份证据只用于**判定既有 ContentBlob 是否仍然成立**，不用于建立新 ContentBlob。建立新 Blob 仍然必须走首次完整 SHA-256，「快速指纹只能筛选候选」这条边界不变。
- `located_unverified` 媒体的行为不变，仍返回 `CONTENT_NOT_VERIFIED`，不进入本 ADR 的读取路径。
- DerivedAsset 生成继续使用经完整校验的本地快照：外部工具需要一个稳定的文件路径，且它是后台 Job 而非每请求路径，全量校验在那里代价可接受、收益明确。

## 理由

- 规范早已要求可直接流式读取时不复制，本决策是让实现回到规范，而不是放宽规范；
- publication 冻结 mtime 后，日常内容替换（重新下载、编辑、覆盖）仍然在发送字节前被干净拒绝，用户可见行为不退化；
- 整文件读取免费复算 digest，使最常见的「看一张图」路径的完整性强度**与旧实现相同**，而代价从 3 倍 I/O 降到 1 倍；
- 只有「Range 请求 + 攻击者刻意保留 size 与 mtime 只改中间字节」这一组合会绕过读取期检测。这正是[测试与发布门禁](../指南/02-测试与发布门禁.md)中「完整性校验能发现同大小、恢复时间戳、采样块相同而中间字节变化的替换」所指向的场景，其权威手段是 `verify` 扫描档案，而不是把每次 Range 请求变成全文件哈希；
- 取消大小上限与空间预检不是降低要求，而是承认它们随复制方案一起消失；把并发闸保留下来，是因为句柄与寻道的有界性在流式方案下仍然真实。

## 替代方案

- **保持每请求整文件复制 + 哈希**：正确性最强，但 `MED-1` 描述的资源耗尽面与 I/O 放大全部保留，且与规范冲突。
- **只做身份证据比对、完全不复算 digest**：最快，但会让「同大小、恢复时间戳」的替换在整文件读取路径上也无法被发现，白白放弃一个零成本的检测点。
- **只对小于阈值的文件复算 digest**：引入一个必须解释、必须调优、且在阈值两侧行为不一致的常量，收益不及「整文件读取时复算」这条自然边界。
- **打开时对 Source 加拒绝写共享（Windows `FILE_SHARE_READ`）**：能消除读取期竞态，但会阻塞 gallery-dl 等外部程序写入用户自己的目录，违反「只读 Source 不干扰用户」的产品边界。
- **把未确认媒体也纳入流式读取**：需要另行裁决 `located_unverified` 正文的对外语义，不在本 ADR 范围，维持现状。

## 影响

- catalog 升至 v13：`media_projections` 新增 `mtime_ns`，从 `source_media` 精确一对一回填；缺少对应行的历史投影保留 0，读取端据此退回 size 与整文件 digest 复算，不伪造证据；
- 新增稳定错误码 `CONTENT_CHANGED`（409）与 `MEDIA_READ_BUSY`（503），进入错误信封 Schema 与 OpenAPI；`CONTENT_CHANGED_DURING_HASH` 继续专用于哈希 Job 期间的并发变化，两者不合并；
- `HEAD` 不再对字节作出断言，这一边界必须写进规范，不得在文档中描述为「HEAD 已校验内容」；
- 并发闸的两个数值是 PRE_FREEZE，冻结条件与阶段 4 其余租约数值一并处理；
- 重新审议条件：出现「Range 请求路径也必须抵抗保留时间戳的替换」的真实需求，或 `verify` 档案被证明无法在可接受周期内覆盖用户库；此时应新增 ADR，而不是悄悄恢复每请求全量哈希。
