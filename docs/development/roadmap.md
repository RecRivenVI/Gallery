# 开发路线

## 背景

当前仓库已经包含较大的后端、Web、验证工具和 Windows 制品代码面，但 API、性能预算、安全、可访问性、升级与发行仍未形成同一候选 RC 的完整证据链。路线图因此按“先冻结范围，再对一个 Windows x64 候选执行完整门禁”的方式组织，而不是继续横向增加功能。

## 目标

- 形成可解释、可备份、Source 零写入的 Windows x64 后端 RC；
- 冻结 RC 所需的产品范围、HTTP/实时契约、Schema 与运行预算；
- 把可选 Web 与便携制品纳入同一个明确候选，而不是以独立演示代替产品验收；
- 完成真实 Pixiv 全量只读扫描、哈希、publication、查询和 Source guard 作为候选 RC 的最后验收；
- RC 完成后再评估其它系统、架构和客户端形态。

## 非目标

- 本路线不加入 Remote/OIDC、公网托管、多租户或 Source 写入；
- 不在 Windows x64 RC 前同步开发或测试非 Windows 平台；
- 不用新增功能掩盖尚未关闭的正确性、性能、安全、恢复或可用性门禁；
- 不以历史测试记录、交叉编译或局部 smoke 代替当前候选的完整证据。

## 阶段

### R0：范围与文档基线

状态：2026-08-01 完成文档与静态事实基线；未运行产品测试。

完成条件：根文档职责清楚；当前事实、决策、计划和历史隔离；所有导航有效；不存在以旧 EV 日志替代源码事实的入口；Windows x64 范围在产品、开发和 Agent 规则中一致。

### R1：契约与冻结清单

状态：待执行。

核对并冻结候选 RC 的 OpenAPI、WebSocket、错误词表、capability、query publication、cursor、规则格式、control/catalog migration 支持范围和 PRE_FREEZE 预算。每项冻结必须有源码事实源和变更规则。

### R2：Windows x64 后端候选

状态：待执行。

关闭后端 Correctness、Source 零写入、取消/崩溃恢复、备份恢复、授权、安全资源上限、查询性能与 degradation 缺口。只在隔离 AppDirs 和显式测试根上验证。

### R3：Web 与 Windows 制品候选

状态：待执行。

对同一后端候选执行双入口功能、弱网、可访问性、真实浏览器、制品完整性、升级、降级拒绝、签名和恢复矩阵。Web 或打包成功本身不等于该阶段完成。

### R4：真实 Source 最终验收

状态：待执行。

在 R1–R3 已完成的候选上执行 Pixiv 全量只读扫描、所需哈希、publication、查询、媒体和全树零写入 guard。该步骤是 RC 交付前的最后门槛，不提前消耗真实 Source 作为日常调试环境。

### R5：RC 后评估

状态：待执行；只有 R0–R4 完成后进入。

依据实际需求重新选择 Linux、macOS、其它架构、桌面壳、安装器与自动更新方案。旧的非 Windows 文件和实验结果只能作为输入，不能自动恢复支持矩阵。

## 完成状态规则

- “已实现”只表示当前源码存在可达路径。
- “已覆盖”要求当前自动化中有明确测试或检查入口。
- “已验证”要求记录当轮命令、环境、输入、结果和限制。
- “阶段完成”要求该阶段清单全部通过，并且没有把失败项移到文字备注中规避。
- “RC”要求 R0–R4 对同一个候选制品成立。

精确门禁见[测试与发布门禁](testing-and-release-gates.md)。
