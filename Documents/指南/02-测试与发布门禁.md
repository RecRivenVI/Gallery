# 测试与发布门禁

> 类型：实施指南。Schema/API 冻结、平台支持和 v1 发布验收以本文为唯一权威来源。

## 测试原则

- 领域不变量和公开契约先于实现细节；
- 合成测试用于可重复和极端边界，真实只读样本用于验证规则覆盖，二者不得互相冒充；
- 平台支持必须在目标系统实际运行；交叉编译只能满足“可构建”；
- 性能报告必须记录样本、硬件、存储、版本、冷/热状态和分位数；
- 生产媒体根只允许只读验证，并用前后清单/guard 证明零变化；
- 高风险真实全库扫描、批量派生和维护任务不作为普通 CI。

| 平台 | Windows 核心 smoke | Windows 完整、Linux ext4、macOS、Docker、SMB 按支持目标 |

## 跨平台一致性与主分支 CI 状态

- Web 格式检查的权威命令只有一条：`web` 目录下的 `npm run format:check`（`prettier --check .`）。根级 `Check.ps1` 与 GitHub Actions 的 Windows、Ubuntu 两个 Job 都必须调用它，不允许某个平台改用别的参数、跳过该步骤或先执行 `prettier --write`。
- 同一提交在 Windows 与 Ubuntu 上必须得到同一结论。结论不一致时，先假定是环境把仓库内容改写成了不同字节（最典型的是检出换行），再考虑代码本身；tracked 文件换行的唯一事实源是 `.gitattributes`，不是任何用户或 runner 的 `core.autocrlf`/`core.eol`。
- `Check.ps1` 在执行任何语言门禁前先断言 tracked 文件的 index 与工作树换行均为 LF，使本地门禁与 CI 在换行问题上等价，失败时直接列出违规文件。
- VitePWA/Workbox 生成的 precache URL 必须非空、按不依赖 locale 的稳定二元序排列且无重复；固定为同一 Node/npm 与 lockfile 时，Windows 和 Ubuntu 构建不得改写 tracked Web 生产资产。生成器升级或资产集合变化后仍由 `internal/webapp` 的最终产物测试和根级生成摘要共同 fail-closed。
- 主分支 CI 失败不得无限期标记为“既有问题”。同一失败签名在 `main` 上连续出现第二次时，必须立即登记为待修复缺陷并在下一轮作为正式任务处理；在其关闭之前，不得声明任何依赖该 Job 的门禁通过，也不得把“CI 一直是红的”当作可接受的稳态。
- 跨平台格式失败只能通过修正仓库事实源解决。禁止把 `endOfLine` 改为 `auto`、删除或跳过某个平台的 Job、对失败命令加 `continue-on-error`、忽略退出码，或把普通源码批量写入 `.prettierignore`。

## 正式验证规模分级

阶段 3、阶段 4 及未来阶段共用同一套规模分级，不按阶段各自定义规模。规模单位是**单个聚合 Catalog
的 WorkProjection 总数**，不是每个来源的数量。

| 等级 | WorkProjection 数量 | 用途 | 是否标准 Gate |
| --- | ---: | --- | --- |
| `smoke` | 1,000 | 工具启动、契约、进程和最小 Correctness | 是 |
| `integration` | 10,000 | 主要过滤、搜索、Cursor、媒体和报告结构 | 是 |
| `preflight` | 100,000 | 正式规模测试前的成本、空间和超时预检 | 是 |
| `reference` | 500,000 | 推荐的正式 Correctness、Reference Performance 和 Degradation 目标 | 是 |
| `nonrecommended` | ≥1,000,000 | 非推荐、显式启用的诊断场景 | 否 |

500,000 是当前推荐的正式验证规模，默认按 10 个目标来源（见下方"目标来源覆盖"）均摊为每个来源
50,000，共 500,000；若事实规则要求个别来源调整分布，可在保持总数 500,000 且每个来源均有实质性
样本的前提下调整，调整原因必须写入 run manifest。

`≥1,000,000` 规模只能作为显式启用的非推荐诊断场景运行，标准命令、CI、默认脚本和 README 快速流程
不得自动生成或运行；框架若保留手工诊断能力，必须要求显式 `--allow-nonrecommended-scale`、显式
`--scale`、显式独立输出目录、显式确认磁盘空间、显式超时，并在控制台和结果中标注
`NONRECOMMENDED_SCALE`——不属于正式支持规模，不构成标准 Gate。此规模分级由 2026-07-21～
2026-07-22 的首轮 1M/10M 实测结果（见 [验证记录 EV-35](../证据/验证记录.md) 与
[阶段3-4大规模测试归档](../证据/阶段3-4大规模测试归档.md)）驱动确立：10M 构建本身即可能超过 120
分钟且峰值占用约 91.47 GiB，1M 完整性能矩阵推算耗时约 97 分钟且高并发场景明确未达标，两者均不
适合作为可重复运行的标准发布 Gate；不代表产品架构确定无法支持千万级规模。

## Walking Skeleton 开工约束

Walking Skeleton 可以在完整 Schema/API 冻结前开工，但切片内已使用的基础契约必须是正式模型：两库迁移框架、Canonical/Source ID、SourceRuleBinding、首次完整 Blob hash、`query_publication_id`、OpenAPI DTO/错误信封和 capability 检查。验收应主动拒绝内存替代库、路径主键、临时 DTO、匿名管理员和客户端直连数据库。尚未实现 FTS、Overlay 写入、快照分页和多强杀点不构成开工阻塞，它们由 Architecture Proof Slice 冻结前补齐。

## 门禁分级

### Correctness Gate

所有正式支持环境必须满足，不能用“设备较慢”降级：

- Source 媒体根零写入，AppDirs 与 Source 不重叠；
- 同一 AppDirs 同时只有一个进程取得写所有权：第二个实例在打开或迁移数据库、建立监听、改写 descriptor 前即失败，锁在进程退出或强杀后释放，遗留锁文件不永久阻止启动，不同 AppDirs 可并行；
- 长任务经有界调度器执行：并发上限、资源类别隔离、取消与 graceful shutdown 生效，队列满不阻塞且持久 Job 保持 queued；同一逻辑 Job 同时最多一个 active Attempt，过期租约由启动及周期 reconciliation 按退避恢复，不丢失 publication 一致性；
- 对外查询只能通过合法 `query_publication_id` 选择快照，不接受裸 revision 组合，也不混合 Catalog、Overlay projection、SortKey 和 FTS 代次；
- 取消、崩溃、磁盘满和跨库 reconciliation 后旧数据仍一致且可解释；
- 取消/完成/失败的 Job 与 active Attempt 必须同事务收敛；retry-backoff 取消不得再次入队，Scan 显式取消必须级联活动 Hash，纯进程关闭只能形成 retryable `PROCESS_INTERRUPTED`；取消先于 `BeginPublishing` 时不得发布，进入 publishing 后拒绝迟到取消，已提交 Catalog publication 必须按权威事实恢复 completed；
- Catalog 删除重建后 Canonical、Binding、Overlay 和固定 Blob 稳定引用不丢失；
- SourceWork 拆分/合并按稳定来源证据检测，无法安全自动处理时经 Binding issue 阻塞该 Source publication，人工决策以 control.db pre-seed Binding 表达；撤回仅适用于尚未被扫描消费的决策，消费后返回 `CONFLICT` 且决策、issue、Binding 不部分修改，已生效结构变化需新的人工决策或未来补偿流程。Catalog 全量重建后决策恢复、Canonical ID 不漂移、被否定候选不复现，其他 Source 不受影响；
- capability、资源范围、Session/Token/WS 吊销不可绕过；
- 路径解析不能越界，句柄复核和离线状态不能退化为不受控读取；
- 所有失败使用稳定 code，不泄露绝对路径、secret、内部 row ID 或私密 metadata。

### Reference Performance Gate

性能阈值只对明确登记的官方参考硬件成立。每次结果必须同时记录 CPU、内存、存储型号/介质、操作系统、SQLite/搜索库版本、冷/热缓存、并发数、样本规模、运行次数和分位数；缺少任一项的旧数字只能作为方向性证据，不能宣称通过正式门禁。

- 500,000 WorkProjection（推荐正式验证规模，见「正式验证规模分级」）、每个投影两条关系、完整 SourceMedia/ContentBlob/FileLocation/FTS，1%/10%/50% 变化的 publication P95 <250 ms；≥1,000,000 属于非推荐诊断场景，其结果只作方向性证据，不代表本 Gate 的通过或不通过；
- 搜索 P95 必须按查询类别、limit、候选量和是否包含原文复核分别设阈值，不能以单个选择性查询代表全部搜索；
- staging 构建、Overlay 重投影、GC、VACUUM、峰值临时空间和完整哈希吞吐必须各有预算；当前证据仅提供基线，正式阈值在参考硬件复跑后冻结；
- **migration 耗时预算属于本 Gate，不属于可移植单元测试**。历史上 `internal/storage` 的合成规模迁移测试用固定 5 秒墙钟作为通过条件，在共享 CI runner 上连续假阳性（同一段迁移本机 NVMe 约 0.04 秒，GitHub Windows runner 实测 22.95 秒与 3.51 秒），改用同机整表改写校准也不成立——该迁移的主要成本是窗口函数排序器的临时文件 I/O，主库页写入无法代表它。单元测试现在只保留与机器无关的 `EXPLAIN QUERY PLAN` 结构断言（每张放大表单侧扫描一次、另一侧索引查找、禁止相关子查询），耗时改为记录值；数值预算在本 Gate 的登记硬件上测定。

EV-39（2026-07-23）核对了这些结论的可复验性：`tools/testlab/stages/stage4` 的查询与媒体 Correctness 断言（约 1,100 行）**没有任何 `go test` 入口**，只能人工 CLI 触发，`go test ./...` 与 CI 都不执行；该目录现有的 `perf_test.go`/`cursor_test.go` 断言的是测试框架自身而非产品。因此 EV-36 的「39 项 Correctness + 6 项 Cursor 通过」是一次性人工快照，不构成持续门禁——在为其建立 smoke 规模自动化入口之前，任何后续提交都不得据此声称阶段 4 Correctness 仍然成立。`internal/query/reference_performance_test.go` 同样默认 `t.Skip`（需 `GALLERY_REFERENCE_PERF=1`），且只输出分位数、没有阈值断言，属测量脚本而非门禁；其默认规模为 100,000，与本文件推荐的 500,000 不一致。

EV-45（2026-07-26）关闭上述 `TEST-2` 持续门禁缺口：`TestStage4CorrectnessSmoke` 现以 1,000 Work、临时 AppDirs、合成 Source、生产 bootstrap 与真实 loopback HTTP/生成客户端，持续执行 39 项查询、6 项 Cursor 和 20 项媒体/DerivedAsset finding；完整 finding 名集合、脱敏报告、首次 index scan 后至按需确认/Derived 完成期间的合成 Source 零写入与零 media limitation 均是普通 `go test` 的失败条件，根级 `Check.ps1`、Windows/Ubuntu CI 和 Linux race 因此会执行该入口。查询报告仍显式登记 `creator.id` 未覆盖；EV-55 已让格式合法但不存在的 `queryPublicationId` 统一返回 OpenAPI 规定的 `409 CURSOR_EXPIRED`，不再保留原“裸伪造 publication 错误码差异”。smoke 不运行 perf，也不替代 500,000 十来源 Correctness、Reference/Degradation Performance、真实 HDD/SMB/NAS 或 API Freeze。

2026-07-23 完成 500,000 规模首次正式验证（见 [验证记录 EV-36](../证据/验证记录.md)）：Correctness（39 项）与 Cursor（6 项）断言全部通过，Perf 矩阵 63 个组合在 25 分钟场景预算内全部完成（未触发 `AbortedByTimeLimit`），但 `wide-cjk`/`structured-and`/`structured-or`/`overlay-favorite` 并发 16 下仍为 2-9.5 秒量级，根因（排序 CTE 无法提前截断、结构化过滤缺索引、`SetMaxOpenConns(4)` 连接池上限）与 EV-35 一致且均未修复；本轮测得的 Stage/Overlay 一次性批量构建耗时与本节定义的"1%/10%/50% 变化 publication P95"不是同一度量，未产出可直接对照该阈值的结果。**Reference Performance Gate 仍未通过。**

**Reference Performance Gate 仍未通过**，不得据此冻结 Ranking/Total/租约数值。

2026-07-27 的 EV-52 增加 catalog v19 候选验证封印与 Overlay candidate 持久创建基线：完整 projection/FTS/成员/封面验证与聚合封面计算
在候选验证 IMMEDIATE 事务内完成；封印是候选完成标记，所有生产 Store 内容写路径都在同一事务核对
staging 状态、候选身份与“未封印”，验证后/发布后的旧 Candidate 一律拒绝原地改写；自然排序启动回填
会在重建事务内撤销遗留封印；

中十次完整验证合计 40.337 s、十次 Publish 合计 7 ms。前者不是完整候选，后者规模不足且只有单次构建，
两者都没有 1%/10%/50% 变化、多样本 P95、并发、峰值空间或 Degradation，因此只证明重操作已经从
publication 事务分离，**Reference Performance Gate 仍未通过**。

### Degradation Gate

HDD、NAS 或低性能设备允许超过参考机性能阈值，但必须保证：

- 旧 `query_publication_id` 在构建、GC 和维护期间仍可浏览；
- 长任务有单调进度、可取消且不长时间持有 publication 锁；
- 空间预检失败时在 publication 前终止，保留旧数据；构建中磁盘满也不得破坏活动 revision；
- 维护窗口、积压和预计空间对用户可见；
- 性能退化不能改变快照、授权、路径安全、错误 code 或崩溃恢复语义。

## 领域 Schema 最终冻结门禁

> 分层说明：阶段 1 Schema Freeze Gate 已冻结**核心领域身份与唯一约束**（见 [领域模型与数据所有权](../规范/03-领域模型与数据所有权.md#schema-冻结分层与仍需确定项) 与 `schema_freeze` 表），其中含 Binding 的 `(source_id, source_key) WHERE status='active'` 唯一与 `(work_id, ordinal)` 唯一。本节是**最终物理唯一约束**冻结门禁，仍未通过；它进一步要求文件身份、超大文件持久哈希、SMB/FileID 降级等证据，未通过前不得冻结 FileLocation 等依赖文件身份的最终唯一约束，但不重开已冻结的核心领域身份。

必须完成：

阶段 6 当前状态（2026-07-27，EV-38～EV-40 + EV-42 + EV-54～EV-58）：React/TypeScript Web/PWA、OpenAPI 生成客户端、同源嵌入资产、静态壳 Service Worker 和结构化错误已形成页面代码基线；Chrome/Edge 的真实 Personal 与 loopback LAN 认证/实时主路径通过。EV-54～EV-57 以隔离 Chromium/真实 `galleryd` 建立管理自举、publication-bound 画廊/媒体、CustomCover 与规则生命周期持续门禁。EV-58 又把无损规则文本、Schema/示例端点、模板选择、CSP 兼容 RJSF/AJV 表单和文本模式切换接到同一 bootstrap；表单与文本模式共享一个 DraftWorkspace/CAS/dirty 状态，规则大整数与高精度小数不先经过 JavaScript `number`。阶段 6 Web Gate **仍未通过**：这些链路不含真实 Source/媒体、任意规则的完整可视化构建、规则回滚/弃用/参数集、其余 v1 管理写路径、WS gap/重连、Firefox、真实移动设备/触控、人工屏幕阅读器、多设备 LAN 或完整性能/安全组合门禁。

EV-39 用真实浏览器复核后，本节此前对「WS→HTTP 恢复已形成正式代码基线」的表述必须修正：`/ws/v1` 在 Chrome/Edge 中 100% 握手失败，前端信封字段名与契约不符，因此该恢复链路**从未在真实浏览器中运行过**；同时 6 个前端 capability 名与后端权威词表不符，使多数写入口不渲染。EV-39 同时暴露三条门禁自身的缺陷，须在扩大 Web Gate 前一并修正：

- CI 唯一的浏览器 Job 原先全程 mock API 并用假 WebSocket 替换 `window.WebSocket`，不接触任何 `galleryd` 代码；真实后端 E2E（`@real`/`@lan-real`）在 CI 中恒跳过。**「mock smoke 通过」必须表述为「静态壳 + mock 契约 smoke 通过」，不得计入 Web Gate 的浏览器证据。**
- mock 套件的合成 bootstrap 自行发明 capability 名，构成自证；今后合成 bootstrap 必须与后端权威词表同源。
- `web/playwright.config.ts` 的 `webServer` 硬编码固定端口并使用 `--strictPort`，端口被占用时整个 smoke 门禁不可运行；门禁必须能在任意干净环境中复现。

EV-40 已关闭后两条：合成 bootstrap 改为直接引用后端权威 capability 词表的前端副本（并由 `internal/auth` 的跨语言测试比对），预览端口默认改为空闲端口；同时新增真实后端下断言 WebSocket 建立、收到事件且零 CSP 违规的本机用例。EV-54 关闭第一条的首个可持续切片：GitHub Actions 浏览器 Job 在 mock smoke 后启动临时 AppDirs、动态 loopback 端口的真实 `galleryd`，复制最小合成 Source 并用 Chromium 执行管理自举 E2E；EV-55 又在同一运行器中增加 real-media 和 real-gallery 两段，EV-56 再增加串联在 real-media 后的 real-custom-cover 段；EV-57 把 bootstrap 内的规则版本/绑定 API 捷径替换为完整规则 UI，EV-58 再把该链起点替换为模板驱动 Schema 表单、文本切换和精确请求体断言。四次调用分别设置预算并保持 Chromium 串行零重试，当前合计 bootstrap 1/1、real-media 1/1、real-custom-cover 1/1、real-gallery 3/3。Source guard 比较文件和目录的相对路径、模式、mtime、大小与摘要，执行前后必须一致。运行器用 Unix 进程组或 Windows 挂起创建后原子纳入 Job Object 回收进程树，设置阶段超时并清理临时目录；真实模式禁用会记录 Cookie/Set-Cookie 的 Playwright 网络 trace，CI 失败 artifact 只允许后端日志、截图和视频白名单。

EV-55 已把 EV-42 的 WorkCover、作品详情和媒体读取部分从组件/Chromium mock 扩展到隔离真实后端，并验证 publication 传播、实际图片解码、正文协议和失效恢复；EV-56 又把 CustomCover 的设置、历史快照冻结、清除回退与 Overlay publication 恢复扩展到同一隔离真实后端；EV-57 再把规则包/草稿/发布/Binding 首链从组件测试扩展到同一真实后端；EV-58 又覆盖模板选择、Schema 表单、无损文本切换和保存/Impact 的精确文本契约。证据仍只来自 Personal/Chromium/合成 Source，不得外推为真实 Source/媒体、任意规则完整可视化构建或完整 Web Gate。

- Web 在无壳普通浏览器完成 v1 业务闭环；

## v1 发布检查单

1. 所有接受 ADR 的契约测试通过；有条件 ADR 在发布说明中明确状态。
2. `control.db` 备份、恢复和失败回滚演练通过；Catalog 删除重建不丢用户事实。
3. 支持矩阵逐项有实际运行证据；未通过平台不写“支持”。
4. 媒体根前后 guard 一致，AppDirs 与 Source 无重叠。
5. OpenAPI、WebSocket、规则 Schema、排序协议和数据 schema 都有版本。
6. 依赖、外部工具、许可证、SBOM、签名和漏洞检查完成。
7. 升级/降级边界、备份要求、重建影响和失败恢复写入发行说明。
8. 未解决门禁有明确 owner、影响和禁用策略，没有“先上线再观察”的静默例外。
9. Correctness、Reference Performance 和 Degradation 三类结果分别报告，不用参考机数字替代慢设备退化验证，也不用慢设备豁免正确性。
